# Техническое ТЗ v1

## 1. Цель MVP

Создать backend ассистента, который умеет:

1. определить класс, предмет и тип педагогической задачи;
2. получить актуальное состояние курса из БД;
3. получить релевантные материалы из библиотеки;
4. сформировать компактный контекст для LLM;
5. создавать уроки и материалы;
6. сохранять план урока отдельно от факта его проведения;
7. после урока обновлять прогресс и следующий шаг.

## 2. Базовый pipeline

`User request`
-> `Router`
-> `Teacher/Class context`
-> `Memory retrieval`
-> `Knowledge retrieval`
-> `Runtime SOP`
-> `LLM`
-> `Quality Gate`
-> `Output`
-> `Memory update`

## 3. Компоненты MVP

### API
FastAPI.

### Database
PostgreSQL.

### Vector search
pgvector. Конкретная модель embeddings не зашивается в схему.

### Files
PDF/DOCX и созданные материалы хранятся вне SQL; БД хранит путь и метаданные.

### LLM
Отдельный provider interface. Бизнес-логика не должна зависеть от одной модели.

## 5. Ключевые инварианты

1. Созданный конспект не означает, что урок проведён.
2. `planned_content` и `completed_content` хранятся отдельно.
3. Основной учебник определяется данными, а не кодом.
4. Актуальные официальные нормы могут иметь приоритет над учебником.
5. Пользовательское исправление данных имеет приоритет над старой записью.
6. GPT не используется как БД.
7. В модель передаётся только релевантный контекст.
8. Персональные данные учеников не смешиваются с базой учебников.
9. VK — `origin` файла, а не показатель авторитетности содержания.
10. Любой важный факт должен иметь источник или подтверждение учителя.

## 6. Runtime SOP

Полные SOP хранятся как документация. В модель передаются только компактные
runtime-правила конкретного типа задачи.

Например, для урока:

- учитывать текущий прогресс;
- опираться на PRIMARY textbook и актуальную ФРП;
- определить цель и измеримый результат;
- связать результат с деятельностью ученика;
- дать реальный тайминг;
- включить практику и контроль понимания;
- выделить записи в тетрадь;
- предусмотреть содержательную рефлексию;
- не считать урок проведённым до подтверждения.

## 8. Definition of Done для технического MVP

MVP считается ожившим, когда запрос:

> «Завтра 9-Б, общество. Сделай следующий урок»

может автоматически:

1. определить курс;
2. получить последний фактически проведённый урок;
3. получить текущее ДЗ и незавершённое;
4. найти основной учебник;
5. найти нужные chunks;
6. собрать prompt;
7. создать готовый сценарий;
8. сохранить его как `planned`;
9. после сообщения «урок провёл...» обновить фактический прогресс.


## 9. Universal Curriculum Layer

Основа публичного продукта: `Subject -> Grade -> Curriculum -> Unit -> Topic -> Outcomes / Concepts / Skills / Sources`. Персональный профиль только адаптирует глобальное содержание.


## 10. Exam Model Layer

Экзаменационные модели версионируются отдельно от учебной программы. Ключевые сущности: `exam_models`, `exam_resources`, `codifier_elements`, `exam_tasks`, `topic_exam_mappings`. Проект КИМ и утверждённая модель являются разными статусами; система не имеет права автоматически повышать `project` до `final`.
